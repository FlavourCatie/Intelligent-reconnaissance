> 场景：`Materials/practice/practice1_Scene`（4794 × 4794 m，1 px = 1 m）

## 0. 一句话概述

**无人机负责"看"，无人车负责"打"**：无人机沿规划航线侦察，发现敌方目标后把坐标回传；
系统在路网上把目标吸附、去重、最优分配给三台无人车；无人车用 A\* 自主规划路径出发，
途中避障、拥堵时超车，到达后停车上报。

整条链路**单进程、单 SDK 客户端、只注册一次节点**，避免重复注册同名节点带来的冲突。

## 2. 已实现的算法

### 2.1 无人机航线规划【组员】

* **安全包络**：把任务区矩形按 `ARENA_MARGIN=10 m` 内缩，把 3 个禁飞区按
  `SAFETY_MARGIN=30 m` 外扩成矩形；矩形外扩一定包住真实的 30 m 偏置（含凹角），
  用"保守但可审计"的近似换取纯标准库实现。
* **可见性图 + Dijkstra**：起点、终点、各禁飞区矩形的 8 个角点构成节点，
  两两之间做"线段是否穿矩形"判定，连边权重为欧氏距离，Dijkstra 求最短路。
  **不允许直飞兜底**——找不到安全路径就报错，不冒险。
* **牛耕式覆盖扫描**（`missions/sweep_plan.py`，本轮新做）：
  侦查开始时敌人位置未知，不能"直奔目标"，必须对区域做覆盖扫描。
  * **条带间距 = 2R**（R 为探测半径 300 m → 600 m）：相邻扫描线的探测圆恰好相切，
    不留漏检带
  * **沿区域长边扫描**：同面积下条带数最少 → 航程最短、转弯最少
  * **禁飞区切开而不绕行**：扫描线在禁飞区内侧被切成若干安全子段，
    只跳过禁飞区本身（两侧照常扫），不会为了绕路破坏覆盖
  * **区域三分**（默认）：把搜索区域按长边**等分成 3 块矩形**，一架机包一块，
    各自在自己块内沿坐标轴做牛耕式扫描 —— 每架只需走 1/3 的距离，
    画面上一眼就能看出"谁负责哪一块"
  * **按航程均衡**（可选 `--sweep-partition strips`）：全局条带再枚举切分 + LPT，
    取"最长那条最短"的分配
  * 输出**三条航点序列**，可直接喂给运动学模型或飞控

  * **搜索区域 = 小地图任务区域**：取「无人机出生点 + 无人车出生点 + 近处敌人」
    的包围盒（加 160 m 余量、最小 ±420 m），扫描与显示用同一个矩形 ——
    扫的就是看到的那一块，不会多扫也不会漏扫
  * **空块回退**：若三等分后某块整块落在禁飞区里（该机将没有航线），
    自动退回"全局条带按航程均衡"，保证三架都有任务

  实测（演示区域 900×900 m，6 条线）：三机航程 **588 / 570 / 558 m（差 5%）**；
  全任务区（4118×1390 m，3 条线）：**4442 / 4254 / 4714 m（差 11%）**，
  15 m/s 下最长约 314 s。

### 2.2 目标探测【组员】

* SDK `detect_situation()`，判定条件：`Type ∈ {strike, enemy, hostile}`、
  `HealthPoint > 0`、与无人机水平距离 ≤ `DETECT_RADIUS = 300 m`。
* 每 `DETECT_EVERY = 10` 帧探测一次，`CLUSTER_RADIUS = 15 m` 内合并重复点。
* 结果写入 `config/detected.json`，供显示端与其他模块热加载。

### 2.3 无人车路径规划【组员】

* **双图**：`skeletonized_image.png`（1 px 宽骨架，用于 A\*）+
  `roadnet_raw.png`（真实路宽，用于判断能否会车/超车）。
* **A\***：8 邻域栅格搜索，支持在线重规划（封格子半径 `BLOCK_R = 10 px`）。
* **路径跟随**：前视点跟踪 + 转向/油门控制；`ARRIVE_DIST = 20 m` 内判定到达。
* **避障与拥堵**：
  * 检测前方路障（`Barricade_BP` 等），触发绕行或倒车退出路口（`REVERSE_OVERSHOOT = 12 m`）
  * 前方队友停死超过 `OVERTAKE_TIMEOUT = 3 s` → **S 形超车**（横向偏移最大 5 m）
  * 速度 < 0.3 m/s 持续 8 s → 判定 `stuck` 上报

### 2.4 通视与地形约束【完善】

* 目标落在**禁飞区**时，无人机规划不出航线 → 撒点阶段就直接排除（多边形外扩 30 m 判定）。
* 目标落在**建筑里**时，无人车开不进去 → 目标坐标先**吸附到最近路网像素**（搜索半径 40 px）再派车。

### 2.5 目标分配【完善】

* 先去重（< 8 m 的视为同一目标）。
* 用**全排列暴力枚举**求"三车总行驶距离最短"的 1:1 匹配
  （3 个目标时最多 6 种排列，计算量可忽略）。
* 目标数 > 车数：只取最优的 3 个；目标数 < 车数：循环分配并提示。

### 2.6 无人机运动学模型【完善】

> 飞控接口不可用时的替代方案（详见第 5 节），但模型本身是完整实现的。

* **转角圆弧**：航线是可见性图的直线折线，每个中间顶点用**二次贝塞尔**做
  30 m 圆角，消除瞬间掉头。
* **等距重采样**：按弧长 1.5 m 重新采样，任意位置切向连续。
* **偏航限速**：`70 °/s`，角差归一到 ±180° 避免翻转。
* **爬升**：`12 m/s` 垂直爬升，**爬到位才开始前进**（避免低速穿楼）。
* **限速位移**：单帧位移上限 6 m，杜绝瞬移（瞬移会产生穿透伤害直接坠毁）。

数值验证（假时钟 700 帧）：单帧位移恒为 0.750 m（= 15 m/s × 0.05 s），
单帧转角 0.282°（限速 3.5°），圆角只让路径缩短 0.5%。

### 2.7 战场态势显示【完善】

* **纯显示层**，不控制任何载具：路网底图、任务区、禁飞区、雷区、电磁区、阶段线。
* 敌人标记**空心 → 实心**表示未发现/已发现；配目标星标与虚线。
* **自动 ROI**：取"无人机出生点 + 无人车出生点 + 近处敌人"的包围盒，
  加 160 m 余量、最小 ±420 m；**搜索区域与显示区域是同一个矩形**（青绿实线框），场景自带的 arena 只画成灰色虚线表示地图边界。
* **无人机配色**：爬升/巡航为彩色（每架一色），航线飞完或损毁转灰；航迹同步变灰。
* 键盘 `1-6` 聚焦、`0` 总览、`+/-` 缩放、`s` 存图。

## 3. 侦查→打击全流程

```
① 阶段解锁
   plan_start → reconnaissance_start/end → vau_reconnaissance_start/end
   （不先解锁，get_road_network() 会返回失败）

② 无人机起飞
   3 架注册（node_no 4/5/6）→ SafePlanner 规划安全航线 → 爬升到 Z = 250 m

③ 沿牛耕式航线巡航侦查
   三机各领一段等长扫描任务，条带间距 2R=600 m
   15 m/s，每 10 帧探测一次（半径 300 m），发现即写入 detected.json

④ 目标汇聚
   发现坐标 → 吸附到最近路网 → 8 m 去重 → 得到"车能开到的"目标点

⑤ 目标分配（触发条件任一）
   · 发现目标数 ≥ 3              ← 正常路径
   · 无人机全部飞完 / 全部损毁   ← 有几个派几个
   · 侦查超时（默认 200 s）

   → 全排列求最小总距离，1:1 分配 → 写 goals.json

⑥ 无人车出击（错峰 4~6 s）
   起步朝向转向目标 → A* 规划 → 行驶 → 避障/超车/会车让行 → 到达或上报

⑦ 收尾
   全部到达/上报，或超过 --ugv-deadline（默认 360 s）
```

### 关键设计取舍

| 决策 | 原因 |
|---|---|
| **单进程单客户端** | 显示端和控制端若各自注册同名节点，行为不可预期 |
| **无人机先爬升再前进** | 低空贴楼飞必然撞楼（实测会掉血归零） |
| **目标吸附到路网** | 敌人常在楼里/路障后，原始坐标车开不进去 |
| **全排列分配** | 3 个目标时计算量可忽略，但能明显减少总行驶距离 |

## 4. 工程稳定性（为演示做的加固）

| 问题 | 现象 | 处理 |
|---|---|---|
| SDK 抢占 `sys.argv` | 带任何参数就报 `unrecognized arguments` | `core/sdk_boot.make_client()` 构造期间收走 argv |
| 启动顺序 | 飞控早于仿真器 → 飞控绑不上飞机 | `core/preflight` 检查进程与启动时间，顺序错就告警 |
| 多实例 | 端口 2000 有两个监听者 → 场景脚本拿不到世界直接退出 | `tools/kill_all.py` 一键清场 + `--check` 体检 |
| 目标占道 | 无人车把"目标本身"当障碍，反复倒车卡死 | 撒点后横向挪到路侧 14~22 m |
| 丁字口掉头 | 三车出生朝向相同，目标在侧支路时必须掉头，路口没空间 | 发车前 `yaw = atan2(dy, dx)` 把车头转向目标 |
| 路口拥堵 | 三车同时出发挤成一团 | 错峰发车 4~6 s |
| 对向相撞 | 双方都判"路被挡"，一个倒一个进 | 会车让行：14 m 内让"离目标更远"的车刹停 3 s |
| 任务不结束 | 个别车一直 `drive`，整轮拖到 900 s | `--ugv-deadline` 超时收尾 |

## 5. 尚未解决的问题：飞控动力学

> **2026-11-02 更新（littleZ05）：本节结论已被推翻，保留原文仅作中期留档。**
>
> 真因不是"SDK 通道不可用"，而是 **工作区路径带空格** —— `driver.exe` 拉起
> ArduPilot SITL 时把命令行拼成一个字符串、`--defaults` 没加引号，空格把
> `--serial0 udpclient:...` 整段吞掉，SITL 退回 TCP 5760，飞控收不到 MAVLink 心跳，
> 于是 `UAV#n: Connect Timeout`、飞机没有动力学实例、`control_kinetic_simply()` 返回 200 但零位移。
>
> 另外 `launch_kinetic` / `get_kinetic_data` 是 V1.4 **主动删除**的接口（SDK 里只剩 `return None`），
> 它们从来不是"启动动力学"的开关，18 组参数枚举注定是空。
>
> 修复与复现：见 [飞控调通_根因与修复.md](飞控调通_根因与修复.md)
> （`tools/sim_link.py --create` 建无空格入口 + `tools/sitl_probe.py` 复核）。
> 下面第 5 节原样保留，答辩时如需口径请以新文档为准。

### 现状

**这套课程包交付的 SDK 里，四旋翼的飞行动力学通道不可用。** 我们做了完整验证：

| 测试 | 覆盖 | 结果 |
|---|---|---|
| `control_kinetic_simply_global(x,y,z,v,ts)` | 多轮，改 z 符号、改速度 | 返回 `(200, ts)`，**位移 0.00 m** |
| `control_kinetic_simply(...)` | 多轮 | 同上 |
| `launch_kinetic(sim_type, count, switch)` | **18 组**（0~5 × 1/3/6） | 全部返回 `None` |
| `get_kinetic_data()`（完整 8 字段） | 每次 | **恒为 `None`** |
| 飞控驱动窗口 | — | `driver.exe` 只有 `SUBCONTROL` 横幅，`main-release.exe` 只有心跳，**从不提及任何飞机** |
| 链路 | — | `driver → main-release:4444`、`carlaue4 → main-release:4443` 均 ESTABLISHED |

结论：**协议层接受指令，但驱动端没有对应的动力学实例可算**，
与《SDK 接口说明 V1.4》中"删除 launch_kinetic / control_kinetic_full / get_kinetic_data"
的记录一致（接口名保留、实现被摘除）。

### 另一层障碍：M10 的物理不可控

即使绕开飞控自己驱动，M10 这个 actor 仍有独立问题——它是 `ACarlaWheeledVehicle` 派生：

| 手段 | 调用结果 | 实际效果 |
|---|---|---|
| 每帧 `set_transform` | 成功 | 位置写进去，但被累积速度覆盖 |
| `set_target_velocity(0,0,0)` | 不报错 | **无效**，速度照涨 |
| `set_enable_gravity(False)` | 不报错（日志有 `GRAVITY OFF`） | **无效**，仍 9.8 m/s² 自由落体 |
| `set_simulate_physics(False)` | — | **UE4 断言崩溃**（`VehicleAnim != nullptr`） |

实测速度累积：0 → 37.6 → 164 → 220 → **456 m/s**，任何"贴着物理写位姿"的做法
都会抖动、撞墙、坠毁。

### 当前方案（中期演示）

**无人机采用运动学模型模拟**（第 2.6 节），位置、航迹、探测判定全部由模型给出，
**不驱动真实 actor**；**无人车完全驱动真实车辆**。

* 优点：算法链路真实、可重复、零崩溃
* 代价：3D 视图中看不到无人机飞行（它只在沙盘上飞）

### 解决进展

* 已定位到"驱动侧无动力学实例"这一层，不再怀疑配置/端口/启动顺序
* 已与组员核对交付文件（怀疑 egg / 驱动打包不完整）
* **新版本 SDK 正在对接，预计近期可恢复真实飞行**；接口恢复后只需把
  `--uav-mode` 从 `virtual` 改回 `kinetic`，`UavRunner` 那条真实飞行路径一直保留未删

### 遗留的次要问题

* 无人车运动学只支持前进 + 倒车退出，**没有三点掉头/倒车入库的几何规划**；
  密集路网里仍可能因转弯半径不足卡住（已用路侧布点、起步转向、错峰发车缓解）
* 避障只处理"前方静态障碍"，对"目标自身占道""对向会车"依赖调度层规则规避

## 7. 答辩口径建议

**问：无人机为什么在 3D 画面里不动？**

> 课程包这套 SDK 的四旋翼动力学通道不可用：控制接口返回 200 但零位移，
> `launch_kinetic` 18 组参数全部返回空，`get_kinetic_data()` 恒为 `None`，
> 飞控驱动窗口只有心跳、从不提及任何飞机。同时 M10 的物理无法关闭
> （关物理会触发 UE4 断言崩溃），实测以 9.8 m/s² 自由落体。
> 因此本期用**运动学模型**驱动无人机（算法链路真实），无人车完全驱动真实车辆。
> 已与组员核对交付文件，新 SDK 正在对接，恢复后改一个参数即可切换回真实飞行。

**问：这套系统"智能"在哪？**

> 三个层面：① 航线按禁飞区做安全规划、按敌人位置动态生成（不是固定巡逻线）；
> ② 目标经"路网吸附 + 去重 + 全排列最优分配"变成三台车各自的可行任务；
> ③ 车端 A\* 在线重规划 + 拥堵超车，调度端错峰发车 + 会车让行。
