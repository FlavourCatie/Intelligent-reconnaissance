# 个人工作亮点总结

---

## 1. 亮点一：顶层设计与指导思想

### 1.1 痛点：为什么不能“发现即派单车”

传统做法通常是“谁近谁去、发现就派”，本质上是平面空间里的贪心分配，存在三个结构性问题：

- **只考虑距离，不考虑路网拓扑**：无人车不能穿越街区，直线距离近不等于实际到达快；
- **只考虑单车，不考虑协同**：三台车各自为战，容易出现“先到先暴露、后到跟不上”；
- **只考虑一次分配，不考虑过程变化**：目标移动、车辆故障、道路被占后，缺少可解释的重分配和降级机制。

因此，我把问题重新定义为：**在骨架路网约束下，把“多车协同打击”拆成可计算、可同步、可降级的三层在线规划问题。**

### 1.2 三层在线规划与解耦架构

将复杂多车协同打击解耦为三层，各层通过标准数据契约 `strike_plan.json` 低耦合交互：

| 层级 | 核心任务 | 关键输出 |
|---|---|---|
| **层 1：动态任务分配** | 事件触发滚动时域分配，回答“谁去打哪个目标” | 目标-车辆配对、阵位、`T*`、`t_go` |
| **层 2：合围阵位生成** | 基于路网拓扑生成封锁位、伏击位与缺口 | `mode`、分支数 `m`、`slots`、`kill_zone` |
| **层 3：同步到达控制** | 集结点等待、速度缩放、`GO` 广播与到位判定 | 集结点、期望速度、到位时间差 |

**三条设计原则：**

- **事件驱动，而非每帧重算**：新目标、目标移动、目标丢失、车辆故障、阵位被占等事件触发重算；配对不变则不重发，避免“车在动、计划在抖”。
- **契约先行，而非模块耦合**：层 1/2/3 只依赖 `strike_plan.json` 的字段约定，支持多模块并行开发与独立验证。
- **可降级，而非理想化**：车辆数不足、阵位被占、目标不可达时，按预设降级表输出保守方案，保证系统“算得出来、说得清楚、退得回去”。

**价值：** 对战术侧，三层结构让“分配—布阵—到位”形成闭环；对工程侧，单次求解保持毫秒级响应，模块可并行、可替换、可单测，显著降低联调成本。

### 1.3 路网约束下的“阵位”与“围三缺一”战术建模

无人车不是在一个自由平面上合围，而是被骨架路网“锁”在分支上。因此，我没有直接套用“圆周合围”，而是把合围建模为**路口分支封锁问题**：

- 以目标所在路口为中心，探测可通行分支数 `m`；
- 按 `m` 与可用车数自适应选择阵位模板；
- 理想态势是“封锁 `m-1` 个分支 + 在缺口纵深设置伏击”，即**围三缺一**；
- 3 台车对 `m=4` 的十字路口，落为 **2 个封锁位 + 1 个伏击位**，而不是机械地要求封住 3 个分支。

在指派目标函数上，采用**瓶颈指派**（最小化最大到达时间 `T*`），而不是最小和指派。原因是合围的暴露窗口由“最晚到位的车”决定，最小和可能让某台车很晚才到，反而拉长整体暴露时间。

**价值：**

- 战术上，把“几何包围”转换为“出口封锁 + 缺口诱敌”，更符合路网条件下的真实可执行性；
- 工程上，阵位可计算、可解释、可降级，避免“目标在路口但车不知道该停哪”；
- 演示上，`m`、封锁位、伏击位、缺口方向都能在计划中直接读出，便于答辩讲清“为什么这么布”。

### 1.4 “领航车-僚车”进场与动态编队机制

在转场与进场阶段，引入“领航-跟随（Leader-Follower）+ 偏置航点”的思想：

- 以领航车的全局 A* 主路径为基准；
- 通过横向/纵向偏置生成僚车轨迹，避免每台车独立规划带来的路径分叉与互相抢道；
- 结合真实路宽图，在“纵队/楔形”之间做自适应平滑切换（一阶插值），兼顾窄路通行与开阔区展开；
- 到达集结点后执行 `split & merge`：先解散编队、各自进入预定阵位，再在 `GO` 时刻同步突击。

**价值：** 转场阶段有队形、有秩序；进场阶段能散开、能占位；既保留领航-跟随的效率，又避免编队僵化导致阵位展不开。

## 2. 亮点二：工程落地突破——多车信息共享与协同状态同步

### 2.1 痛点：多车协同的“信息孤岛”

多车系统最容易出现的问题不是“单车不会开”，而是：

- 每台车只知道自己看到的目标，全局目标表不一致；
- 车辆位姿、占路状态、故障状态不同步，规划层拿到的是“过期世界”；
- 没有统一的承诺等级，已占位的车被反复改派，造成任务抖动；
- 没有统一的 `GO` 时刻，三台车先后暴露，合围变成“排队送”。

### 2.2 具体实现与机制

我推动建立了基于统一数据契约的信息共享链路，核心是“**不重构底层传输协议，也能实现跨模块、跨车辆状态同步**”：

- **统一契约**：目标信息走 `detected.json`，打击计划走 `strike_plan.json`，车辆状态按约定字段上报；
- **原子写 + mtime 热加载**：写入方先写临时文件再原子替换，读取方按文件修改时间热加载，避免“读到半截 JSON”；
- **共享内容**：目标坐标与状态、车辆实时位姿、占路/障碍状态、任务承诺等级 **L0~L3**；
- **协同动作**：基于共享状态实现集结点等待（Hold Point）、时间缩放调速、`GO` 同步突击广播；
- **防抖机制**：承诺等级与配对稳定性结合，已占位/突击中的车不被随意改派，减少“计划反复、车辆来回跑”。

**承诺等级的作用：**

| 等级 | 含义 | 调度含义 |
|---|---|---|
| **L0** | 空闲/不可用 | 可参与新分配 |
| **L1** | 已接令、在途 | 可被更优方案抢占，但有代价 |
| **L2** | 已到集结点/已占位 | 不参与改派，等待 `GO` |
| **L3** | 突击中 | 锁定，避免临门改派 |

**价值：**

- 把“单车感知”升级为“全局一致态势”，规划层不再基于过期信息做决策；
- 用承诺等级和 `GO` 广播消除“先后暴露”和“任务抖动”；
- 原子写 + mtime 的方案改动小、可回退，适合课程设计周期内的快速集成；
- 计划、事件、到位时间差都可落盘，答辩时能复盘“为什么改派/为什么没改派”。

## 3. 亮点三：AI 辅助敏捷工程方法论

### 3.1 核心定位

在有限研发周期内，我探索并实践了一套“**方案设计 → 视频 Demo → 最小闭环 → 可视化录屏 → 迭代增强**”的 AI 辅助复杂系统开发范式。它的重点不是“让 AI 代写代码”，而是**用 AI 压缩设计、沟通、验证三个环节的试错成本**。

### 3.2 五步演进闭环

1. **顶层方案设计（Design First）**  
   借助 AI 梳理领域文献、系统痛点与边界条件，先沉淀《无人车动态合围打击算法选型与编队方案》等设计文档，明确“做什么、不做什么、失败怎么降级”。  
   **产出：** 设计文档、数据契约、降级表。  
   **价值：** 避免一上来写代码，返工成本前移。

2. **概念视频 Demo 验证（Rapid Video Prototyping）**  
   在重型仿真代码之前，先做动态演示 Demo，把“三层架构、围三缺一、同步到达”的战术预期可视化，让团队先对齐“看起来对不对”。  
   **产出：** 概念演示视频、路线/阵位示意。  
   **价值：** 降低沟通成本，提前暴露“路线穿目标”“阵位挤在一起”等设计问题。

3. **最小闭环实现（MVP / P0 落地）**  
   聚焦核心链路：阵位生成 + 3×N 指派 + 同步到达，先跑通“目标确认 → 多车合围”的最小可用闭环，不追求一次做全。  
   **产出：** 可运行的合围计划与执行链路。  
   **价值：** 尽快拿到端到端反馈，而不是在单模块里过度打磨。

4. **可视化效果录屏（Visual Verification）**  
   对核心场景录制小地图/仿真可视化视频，用画面支撑阶段汇报，也用于定位“车是否贴路、阵位是否合理、同步是否成立”。  
   **产出：** 答辩视频、关键帧、路线示意图。  
   **价值：** 让“算法正确”变成“肉眼可验证”，减少口头解释。

5. **渐进式功能迭代（Iterative Enhancement）**  
   在稳定闭环上逐步叠加滚动时域重分配、承诺防抖、局部互避、特殊情景处置等能力，保持每轮都可演示、可回退。  
   **产出：** 分阶段增强的功能清单与验证记录。  
   **价值：** 用可控增量替代“大爆炸式重构”，降低结课前的集成风险。

### 3.3 方法带来的实际收益

- **缩短从想法到可演示的时间**：先对齐，再实现，减少“做完才发现方向不对”；
- **让答辩材料前置沉淀**：设计文档、示意图、视频、关键帧同步产出，最后不用临时补材料；
- **让问题更早暴露**：视频 Demo 阶段就能发现路线、阵位、同步等战术问题；
- **让迭代可回退**：每轮只增强一个点，保留最小闭环作为稳定基线。

## 4. 答辩口径建议

### 30 秒版

> 我主要做了三件事：第一，把多车合围拆成“动态分配—阵位生成—同步到达”三层，用 `strike_plan.json` 解耦；第二，打通多车信息共享和 L0~L3 承诺等级，让三车从各自为战变成同步突击；第三，用“设计—视频—MVP—录屏—迭代”的 AI 辅助流程，缩短从方案到可演示系统的周期。

### 3 分钟展开顺序

1. **先讲痛点**：为什么“发现即派单车”在路网约束下不成立；
2. **再讲框架**：三层各做什么、靠什么契约交互、失败怎么降级；
3. **重点讲阵位**：`m` 分支、围三缺一、瓶颈指派，为什么不是圆周合围；
4. **讲协同**：L0~L3、Hold/GO、原子写 + mtime，解决了什么抖动；
5. **最后讲方法**：视频 Demo 和最小闭环如何降低返工，落到可展示的成果。

### 答辩时建议主动说明的边界

- 当前重点是“算法与协同闭环”，车辆运动学、避障和真实场景执行仍依赖对象层/仿真环境；
- 视频 Demo 用于验证战术逻辑与展示效果，不替代真实标定；
- 三层框架保留了降级与扩展接口，后续可继续接入更精确的车辆动力学、通信延迟和在线感知。
