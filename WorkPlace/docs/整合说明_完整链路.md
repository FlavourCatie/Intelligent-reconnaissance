## 三、我对组员代码做的两处改动（透明说明）

### 1. `control_uav.py`：无人机指令返回码的位置

原实现：

```python
result = ...control_kinetic_simply_global(...)
if not result or result[0] != 200:      # 只认第 0 位
    raise SafetyError(...)
```

问题：同一个 SDK 里状态码位置并不统一——

| 方法 | 封装层怎么用的 | 状态码位置 |
|---|---|---|
| `apply_vehicle_control` | `_, status_code = ...` | **第 2 位** |
| `control_kinetic_simply` | 官方文档列 `code, frame_timestamp` | 第 1 位（推测） |

如果真机是 `(时间戳, 状态码)`，原判断会**把每一次成功都当成失败** → 无人机永远起飞不了。
而组员说明里写着"未执行真实飞行"，所以这点没被实机验证过。

改成前两位出现 200 即视为成功（时间戳不可能是 200 ms）：

```python
if not isinstance(result, (tuple, list)) or 200 not in list(result)[:2]:
```

**联调时如果无人机不动**，先看日志里有没有 `rejected flight command`。

### 2. `control_ugv.py`：路网图片路径

原代码假设两张 PNG 与 `.py` 同目录；整合后图片放到了 `WorkPlace/assets/`，所以改成：

```python
_ASSETS = os.path.join(os.path.dirname(_HERE), "assets")
SKL_PNG = os.path.join(_ASSETS, "skeletonized_image.png")
RAW_PNG = os.path.join(_ASSETS, "roadnet_raw.png")
```

## 四、链路时序

```
① 阶段解锁（plan_start → reconnaissance_* → vau_reconnaissance_*）
      ↓  不先跑这个，get_road_network() 会返回失败（无人车组员的实测结论）
② 无人机：3 架注册（node_no 4/5/6）→ 规划安全航线 → 起飞到 Z=250
      ↓  每 10 帧探测一次（半径 300 m，只认 Type=strike）
③ 发现目标 → 写 config/detected.json（组员实现）→ 我同步到小地图（空心→实心）
      ↓  攒够 --min-targets 个
④ 目标坐标吸附到最近路网 → 贪心分配给三台无人车（最小总距离）
      ↓  同时写进 config/goals.json，星标与实际目标一致
⑤ 三台无人车各自 A* → 行驶 → 遇障在线重规划 → 到达/上报
      ↓
⑥ 主循环每帧：UAV 一帧 → UGV 一帧 → 小地图刷新（20 Hz）
```

**设计要点**：单进程、单 `SwarmAEClient`、**只注册一次**。
这样就不会出现"显示端和控制端重复注册同名节点"这个组员文档里点名要求核实的问题。

## 五、目标分配怎么做的

1. 无人机给的坐标是**敌人所在位置**（常常在楼里/路障后），车开不进去。
   所以先 `nearest_road()` 吸附到最近的路网像素（搜索半径 40 px），再转回世界坐标。
2. 吸附后去掉相距 < 8 m 的重复点。
3. 若可用目标点 ≥ 3：枚举所有「3 点组合 × 6 种排列」，取总直线距离最小的一组。
4. 若不足 3 个：循环分配（多余的车间一目标），日志会提示——
   这时靠吴羽桐实现的**超车逻辑**避免堵死。

## 九、最常见故障：无人机一动不动（飞控驱动没跑）

### 现象

```
[mission] 开始：无人机起飞侦查（Z=250，15 m/s）
[mission] 发现目标 #7 敌方装甲车 (-1829.6, -500.7)
（然后控制台没有更多输出；小地图上三架无人机停在起点不动）
```

### 实测证据（2026-10-28 真实故障）

无人机日志 `codex_outputs/uav_module/run_uav_*.log` 里：

```
frame=1649  positions={'UAV1': (-1875.19, -521.90, 100.0), ...}   ← 82 秒后 z 仍是 100.0
            phases={'UAV1': 'takeoff', 'UAV2': 'takeoff', 'UAV3': 'takeoff'}
```

同时查系统进程：

```
CarlaUE4      运行中
main-release  未运行      ← 飞控驱动没起
driver        未运行      ← 飞控驱动没起
config.yaml   Type: quadrotor   ← 机型配置本身是对的
```

### 原因

四旋翼的运动**不是** CARLA 物理直接算的，而是由 `start.bat` 启动的
**外部飞控驱动**（`main-release.exe` + `driver.exe`）计算后回写。

驱动没跑时，`control_kinetic_simply_global()` 会**返回成功但不产生任何运动**——
高度、位置一动不动，**也没有任何报错**。所以看起来就是"程序卡住了"。

**无人车为什么不受影响**：车走 `apply_vehicle_control()`，直接在 CARLA 里跑，
不经过飞控驱动。这就是"车能动、机不动"的原因。

### 解决（两个层都要查）

**第一层：启动顺序。** 课程文档两份说法不一致，实测以 `kyxz.md` 为准：

| 文档 | 写的顺序 |
|---|---|
| `Materials/readme.txt` | start.bat → CarlaUE4 → subject4.exe |
| `environment_forclass/environment/kyxz.md`（**D4 组别说明**） | **CarlaUE4 → start.bat → subject4.exe** |

2026-10-28 复现时，进程启动时间是：

```
driver        14:23:40
main-release  14:23:39
CarlaUE4      14:24:11      ← 飞控比世界早 32 秒
```

飞控世界里还没有车的时候启动，它就绑不上后面才由 subject4 生成的飞机。
所以正确顺序是：

```powershell
1) CarlaUE4
2) Materials\simu_driver_windows\start.bat     ← 选 2（旋翼），一直开着
3) Materials\practice\practice1_Scene\subject4.exe
4) python WorkPlace\missions\full_mission.py
```

**第二层：如果顺序正确还是不动**，单跑 30 秒诊断：

```powershell
python WorkPlace\tools\uav_diag.py takeoff
```

它会先打印进程/顺序检查，再命令 1 架机原地爬升并每秒打印高度：

* **高度在涨** → 飞控正常，问题在航线/安全边界
* **高度不动** → 驱动确实没生效，看 `start.bat` 那两个黑窗口有没有报错

### 自动检查：`core/preflight.py`

不依赖 `tasklist`（某些环境会被拒，导致误报"驱动没跑"），
改用 Win32 Toolhelp 快照 + `GetProcessTimes`，能同时判断**在不在跑**和**启动先后**：

```
启动前置检查：
  CarlaUE4.exe     运行中
  main-release.exe 运行中
  driver.exe       运行中
  subject4.exe     未运行
  !! 启动顺序：飞控早于 CarlaUE4（这是错的）
  !! 启动顺序疑似反了：飞控驱动比 CarlaUE4 早 32 秒启动。
```

单独跑一次：

```powershell
python WorkPlace\core\preflight.py
```

`full_mission.py` 和 `tools/uav_diag.py takeoff` 启动时都会自动调用它。

### 已经加的三道防线（避免再花 82 秒才发现）

| 防线 | 行为 |
|---|---|
| **启动预检** | 开机就用 `tasklist` 查 `main-release.exe` / `driver.exe`，没跑就打印大字警告 + 正确启动顺序 |
| **控制台心跳** | 每 5 秒一行：`t=10s 机高=[100.0,100.0,100.0]/250 阶段=take,take,take 已发现=1` —— 一眼看出"是不是在爬升" |
| **起飞超时自检** | 60 秒还停在 `takeoff`，直接打印"命令成功但高度没变，基本确定是飞控驱动问题"+ 日志路径；再等 60 秒仍不动就停飞（已有目标时后续流程照常） |

相关参数：

```powershell

python WorkPlace\missions\full_mission.py --console-every 2      # 心跳更密
python WorkPlace\missions\full_mission.py --ignore-driver-check   # 跳过进程预检
```

## 十、飞控动力学不可用时的兜底：`--uav-mode kinematic`

### 先把基础设施排除掉（都有证据）

| 检查项 | 结果 | 依据 |
|---|---|---|
| 飞控进程 | 运行中 | `main-release.exe` / `driver.exe` |
| 启动顺序 | 正确 | CarlaUE4 早于飞控（`preflight` 判定） |
| 端口 | 全部就位 | 2000=CarlaUE4、3301/3302=driver(UDP)、4444=main-release |
| 链路连接 | **全通** | `carlaue4 → main-release:4443` ESTABLISHED；`driver → main-release:4444` ESTABLISHED |
| 机型配置 | quadrotor | `bin\driver\config.yaml` |
| 节点绑定 | 正确 | actor `type_id=vehicle.hrt.m10`，`health=100` |
| actor 可动 | **可动** | `set_transform` 搬 10 m 立即生效 |

### 问题定位在 SDK 的动力学接口：空壳

| 探测 | 结果 | 说明 |
|---|---|---|
| `control_kinetic_simply_global(...)` | `(200, ts)` | 通道接受，但不产生运动 |
| `control_kinetic_simply(...)` | `(200, ts)` | 同上 |
| `control_kinetic_simply_global(..., v=15)` | `(200, ts)` | 同上 |
| `control_kinetic_simply_global(x, y, -z, ...)` | `(200, ts)` | 换坐标系符号也不行 |
| `get_kinetic_data()` | **`None`** | 文档说返回 8 个字段 |
| `launch_kinetic('四旋翼', 1, 1, ts)` | **`None`** | 连非法参数都不报错 |

`launch_kinetic` 对**任意参数**都静默返回 `None`，真实现不可能这样。
这与《SDK 接口说明 V1.4》中"**删除 SwarmAENode 类中的 launch_kinetic、
control_kinetic_full、get_kinetic_data 接口**"的变更记录完全吻合：
方法名留着、函数体被移除。

另外 `set_transform` 之后 z 从 100.0 掉到 99.21 —— 一旦被碰醒就自由落体，
说明**物理是开的、但没有升力**，即没有任何飞控在算。

### 运动学播放的三个实现细节（都踩过坑）

| 细节 | 为什么 |
|---|---|
| **按墙上时钟推进**（`now - last_step`），不是固定 `dt` | 一开始按帧推进，开了小地图后帧率下降，无人机在真实时间里变成蜗牛 |
| **探测按时间兜底**（每 0.5 s 至少一次，另有每 10 帧一次） | 低帧率时"每 10 帧探测一次"采样太稀，150 m/s 下会直接飞过目标 |
| **提供 `last_goals`**（当前飞向的航点） | 显示层要用它画目标星标；`UavRunner` 有、运动学版一开始漏了，一开小地图就 AttributeError |

> 第三条是真实故障：`--uav-mode kinematic` 首次运行时在
> `full_mission.py:560  g = runner.last_goals.get(n)` 崩掉。
> 现在两种 runner 都提供该字段，且显示层用 `getattr(runner, "last_goals", {})` 兜底——
> **显示层缺字段不该把整条任务链带崩**。

### 消除"抽搐"的四个参数

运动学播放最初很抖，原因有两个：航点是直线折线（到点瞬移掉头）+
位姿更新跟着主循环走（小地图一画慢，步长忽大忽小）。现在：

| 参数 | 取值 | 作用 |
|---|---|---|
| `CORNER_RADIUS` | 30 m | 每个中间航点用二次贝塞尔做圆角，消除瞬间掉头 |
| `SAMPLE_SPACING` | 1.5 m | 按弧长等距重采样，任意位置切向连续 |
| `YAW_RATE` | 70 °/s | 偏航角限速 + 角差归一化，避免 ±180° 处翻转 |
| `MAX_DT` | 0.15 s | 单帧最多推进 0.15 s，卡顿时宁可慢一点也不要瞬移 |

另外运动学模式把主循环节拍从 50 ms 提到 **20 ms（50 Hz）**，小地图默认改成
每 4 帧画一次（避免绘图本身拖慢帧率）。真机模式仍按协议的 50 ms。

`selftest/test_kinematic_smooth.py` 做了**数值验证**（不靠肉眼）：

```
稳定 20 Hz：单帧位移 0.7500 m（= 速度×dt）  单帧转角 0.282°（上限 3.5°）
帧率乱跳：  单帧位移 2.2500 m（钳在 15×0.15） 单帧转角 2.141°（上限 10.5°）
圆角代价：  路径 4502.9 m → 4480.5 m（只短 0.5%）
```

## 十一、坑：SDK 会解析 `sys.argv`，带参数就报错

### 现象

```powershell
python .\missions\full_mission.py --uav-mode kinematic
usage: full_mission.py [-h] [-i IP] [-p PORT] [-s SUBJECT] [-n NUMBER] [-t TEAM]
full_mission.py: error: unrecognized arguments: --uav-mode kinematic
```

注意 usage 行里的 `-i/-p/-s/-n/-t` —— **这不是本脚本的参数**，是 SDK 的。

### 原因

`SwarmAEClient.__init__` 内部会调用 `__get_args()`，用 argparse **直接解析整个
`sys.argv`**，而且只认它自己那五个参数。只要我们的脚本带了任何自定义参数，
一构造客户端就被它拒掉。

**为什么之前一直没暴露**：之前都是不带参数直接跑（`sys.argv = ['full_mission.py']`），
SDK 解析当然通过。一旦加 `--uav-mode` / `--min-targets` 这类参数就会炸。
组员交付的 `control_uav.connect_uavs()` 里其实早就为此做了同样的规避
（注释写着 "Some supplied SDK modules parse sys.argv when imported"）。

### 修复

新增 `core/sdk_boot.py`，在构造期间把 argv 临时截成只剩程序名：

```python
from core.sdk_boot import make_client
client = make_client(args.host, args.port)     # 内部保护 argv，构造完还原
```

已改到 4 个入口：`full_mission.py`、`tools/uav_diag.py takeoff`、
`python WorkPlace\tools\uav_diag.py kinetic`。

### 回归测试

`selftest/test_argv_boot.py` 让假 SDK **模拟真机的这个行为**
（设 `FAKE_SDK_PARSE_ARGV=1` 就打开），三步验证：

```
1) 直接构造  → 如预期被 SDK 拒掉（复现报错）
2) make_client → 成功，且 sys.argv 已还原
3) 带参数跑 full_mission.main() → 全程无异常
```

**以后谁写新脚本要连 SDK，一律用 `make_client()`，别直接 `SwarmAEClient(...)`。**

## 十三、三个实测问题的修法（2026-10-28）

### 1. 无人机 Z 轴上下抖

日志里 `机高=[100.0, 100.0, 100.0]` 始终不变，说明我们的写入是稳的 ——
抖动来自**飞控驱动在 5 Hz 改写 actor 位姿**（`config.yaml: SamplingPeriod_ms: 200`），
我们和它抢同一个 actor。

```powershell
python WorkPlace\missions\full_mission.py --uav-mode kinematic --freeze-driver
```

`--freeze-driver` 会在开始前结束 `main-release.exe` / `driver.exe`。
它们对运动学模式毫无用处（动力学接口本来就是空壳），结束掉就没人抢位置了。
代价：真实飞行不可用，要恢复请重开 `start.bat`。

### 2. 无人机总是绕远路

原来用 `cu.search_routes()`，那是 `game.json` 里**固定的条带图案**，和敌人在哪毫无关系，
每次都是同样 7/7/9 个航点、绕三四公里。

现在默认 `--uav-route enemies`：直接按 `targets.json` 里敌人的实际位置排航线
（就近分配 → 每机串 1~2 个目标 → 每段都过 `planner.route()` 绕禁飞区）。

实测从 `7/7/9` 降到 `3/3/1`，发现目标几乎即时。

```powershell
python WorkPlace\missions\full_mission.py --uav-per-target 2   # 每机串几个目标
python WorkPlace\missions\full_mission.py --uav-route strips   # 想回到原来的条带图案
```

落在禁飞区/安全余量里的目标会被自动剔除，不会让整段航线规划失败。

### 3. 无人车反复倒车最后撞停

日志特征：

```
[UGV1] 路障挡路 类型=Barricade_BP 路障=(-1805.5,-522.3) 距路径 4.1 m
[UGV2] 绕行需倒车 44.9 m 退出死路
[UGV2] 疑似撞停(速度<0.3 持续 8s)。位置(-1891.1,-516.9)
```

**原因是敌人本身就是路障**（`dynamic.prop.barricade`）。无人车的避障逻辑把它当成
挡路的实体障碍，于是试图绕行/倒车，最后撞停在路边。

修法：不要用 `barricade` 当敌人类型。

```powershell
python WorkPlace\tools\spawn_targets.py --scene Materials\practice\practice1_Scene ^
  --count 5 --near -1275,-517 --radius 600 --types dynamic.prop.soldier
```

`demo_midterm.py` 的默认 `--types` 已改成 `dynamic.prop.soldier`。

> 另外注意：敌人若正好坐在无人车**唯一出口**的路上，任何类型的避障都可能触发。
> 撒点中心建议离 UGV 出生点远一点（默认 `-1275,-517` 已经预留了距离）。

## 十四、飞控驱动在跑"零推力动力学"——这才是抖动/撞墙/坠毁的总根源

### 现象链

```
t= 0s  机高=[100.0, 100.0, 100.0]   阶段=crui,crui,crui
t= 6s  机高=['?', '?', '?']         阶段=crui,dead,dead     ← 6 秒内两架就没了
```

我们每帧把位置设到 250 m，可无人机会**自己往下掉**。

### 原因

`driver.exe` / `main-release.exe` **一直在跑动力学仿真**，只是我们发的
`control_kinetic_simply_global` 是空壳（返回 200 但不生效），所以它解算出来的
**推力恒为 0** —— 飞机只会往下坠。

于是同一个 actor 上有两拨人写位姿：

| 谁 | 频率 | 写的值 |
|---|---|---|
| 我们 `set_transform` | 50 Hz | 航线上 z=250 的位置 |
| 飞控驱动 | 5 Hz（`SamplingPeriod_ms: 200`） | 它自己解算的"正在下坠"的位置 |

结果：上下抖 → 撞进建筑 → 掉血归零 → `get_location()` 抛异常（心跳显示 `?`）
→ 探测全部失效 → 没有目标 → 无人车不动。

### 修法：运动学模式默认停掉飞控驱动

```powershell
python WorkPlace\missions\full_mission.py --uav-mode kinematic
# 现在默认会先 taskkill driver.exe / main-release.exe，日志会写：
#   运动学模式：先停掉飞控驱动（否则它会和 set_transform 抢位姿）
```

想保留驱动（不建议）：

```powershell
python WorkPlace\missions\full_mission.py --uav-mode kinematic --keep-driver
```

> ⚠️ 停了驱动之后**真实飞行彻底不可用**。要恢复，重开
> `Materials\simu_driver_windows\start.bat`（选 2 旋翼）。

### 为什么不能直接用"动力学飞行"

`--uav-mode kinetic` 走的是真实飞控，但 `control_kinetic_simply_global()`
在这个 SDK 版本里是空壳：返回 `(200, ts)`，高度却一动不动（`tools/uav_diag.py takeoff`
实测 20 秒 Δz=0.00 m）。所以动力学模式下的飞机**没有推力**，起飞就坠毁。

等哪天课程方给出能用的飞控接口，把 `--uav-mode` 改回 `kinetic` 即可，
`UavRunner` 那条路径一直是保留的。

## 十五、无人车什么时候才会出动

触发派车需要**满足任一条件**：

| 条件 | 说明 |
|---|---|
| 发现目标数 ≥ `--min-targets`（默认 3） | 正常路径 |
| 无人机已飞完全部航线 / 全部损毁 | 有几个派几个（不足 3 个也派），日志会写"无人机已无更多可侦查目标" |

所以你那次 `已发现=2` 而车不动，是因为 `--min-targets 3` 没满足、且无人机还没结束。
现在加了"无人机结束后就派车"，即使只有 1~2 个目标也会出动。

## 十六、飞控动力学：最终结论（2026-10-28，证据已完整）

### 全部尝试与结果

| 测试项 | 覆盖范围 | 结果 |

- 这与《SDK 接口说明 V1.4》中"删除 SwarmAENode 类中的 launch_kinetic、

## 十七、开局坠毁的真正原因：**一帧之内瞬移 240 m**

日志：

```
t= 0s  机高=[10.0, 10.0, 10.0]/250     ← vehicles.json 里就是 10 m
t= 5s  机高=['?', '?', '?']            ← 5 秒内两架 dead
```

`start()` 里我把飞机**一帧之内从 10 m 拉到 250 m**。对这种带物理的车 actor，
240 m 的瞬间位移会产生巨大穿透→冲击伤害→血量归零→actor 失效。
（这也是为什么 `UAV LOST` 里写的是"多半是撞楼掉血归零"——其实是被瞬移撞死的。）

### 修法：改成爬升，并给单帧位移设上限

| 参数 | 值 | 作用 |
|---|---|---|
| `CLIMB_RATE` | 12 m/s | 垂直爬升速度，10 m→250 m 约需 20 秒 |
| `MAX_STEP_M` | 6 m | 单帧水平位移上限，杜绝任何形式的瞬移 |

爬升期间**原地不动**（不沿航线前进），到位后才开始巡航，相位显示 `climb`。

数值验证（假时钟，700 帧）：

```
起飞前 z=10.0  climbed=False
爬升后 z=250.0  climbed=True
单帧最大高度变化 = 0.600 m（上限 12×0.05=0.600）
前 5 帧高度：[10.6, 11.2, 11.8, 12.4, 13.0]
```

### 另外：任务不再"永远不结束"

新增 `--ugv-deadline`（默认 300 s）：派车后超过这个时间就收尾。
个别无人车会一直 `drive`（绕路/被堵），以前整轮会拖到 `--duration`（900 s），
看起来像卡死。

```powershell
python WorkPlace\missions\full_mission.py --ugv-deadline 120   # 想更快收尾
```

## 十八、"无人机一直往初始位置掉"的真正原因：**速度在累积**

观察：无论怎么改，飞机总是往出生点（地面）方向去。

原因不在重力大小，而在 **`set_transform()` 只改位置、不清速度**：

1. 我们每帧把飞机写到 250 m
2. 两次写入之间，物理按重力给刚体累加速度（v += g·dt）
3. 下一帧物理先按"累积速度"把它甩下去，我们再写回去
4. 速度越积越大 → 每次被甩得越远 → 表现为"一直往地面/初始位置掉"，
   而且一旦位移过大就撞出致命伤害（`UAV LOST`）

### 修法：每帧把速度清零

```python
actor.set_transform(...)              # 摆到航线上
actor.set_target_velocity(0,0,0)      # 关键：把物理速度清掉
```

`libcarla` 里确认存在 `set_target_velocity`（扫 `swarmae_lib` 的 `.pyd` 得到）。
清零后重力无法累积，飞机就稳在我们放的位置上。

这比"关物理"安全得多：**`set_simulate_physics(False)` 会触发 UE4 断言**
（`VehicleAnim != nullptr`，M10 派生自 wheeled vehicle），直接把仿真器搞崩。
清零速度不动物理开关，效果等价于"把重力影响抵掉"。

### 心跳里新增速度读数

```
[mission] t=  5s  机高=[70.0, 70.0, 70.0]/250  速度=[0.0, 0.0, 0.0]  阶段=climb,climb,climb
```

* `速度=[0.0, 0.0, 0.0]` → 清零生效，飞机是"钉"在航线上的
* `速度=[9.8, ...]` 或很大 → 清零没生效，检查 actor 是否暴露了 `set_target_velocity`

## 十九、结论：这批 M10 actor 的物理不可控 → 改用 `virtual` 模式

### 实测速度累积（飞控已经停掉的情况下）

```
t= 0s  速度=[0.0,   0.0,   0.0]
t= 5s  速度=[37.6,  37.6,  37.6]
t=10s  速度=[60.7,  60.7,  60.7]
t=15s  速度=[164.0, 164.0, 164.0]
t=20s  速度=[220.4, 220.4, 228.2]
t=41s  速度=[366.1, ...]
```

这是 **9.8 m/s² 的自由落体**。注意：此时 `driver.exe` / `main-release.exe`
**已经被结束**（日志里有"已结束飞控驱动"），所以**不是飞控在拽，是物理引擎的重力**。

### 三条路都堵死了

| 尝试 | 结果 |
|---|---|
| 每帧 `set_transform` 写位置 | 位置能写进去，但速度照样累积 → 下一帧被甩得更远 |
| 每帧 `set_target_velocity(0,0,0)` 清速度 | **无效**，速度照涨（这批 actor 无视该调用） |
| `set_simulate_physics(False)` 关物理 | **UE4 直接崩溃**（`VehicleAnim != nullptr`） |

结论：**这个 SDK 里的 M10 无法做稳定的三维运动。** 不是配置问题，是 actor 本身。

### 解法：`virtual` 模式（完全绕开物理）

```powershell
python WorkPlace\demo_midterm.py          # 默认已经是 virtual
```

`--uav-mode virtual` 的做法：

* **位置**：沿航线用数学插值算，不写任何 actor
* **探测**：按数学位置算"目标是否在 300 m 内"，语义与真机一致
* **发现/发布/派车**：完全走原有链路，`detected.json` 照常写

于是：**小地图上的航迹、发现顺序、派车逻辑全部真实且稳定**，
不受物理影响，不会抖、不会坠、不会崩。

代价（必须如实说明）：**仿真画面里的三架飞机不会移动**（它们会自由落体）。
如果演示要求"3D 画面里看到无人机飞"，这个包做不到——因为它的物理关不掉、
速度清不掉、飞控又是空壳。

### 三种模式怎么选

| 模式 | 能飞吗 | 稳定性 | 用途 |
|---|---|---|---|
| `kinetic` | ❌ 飞控空壳 | — | 等课程方修 |
| `kinematic` | ⚠️ 会抖会坠 | 差 | 不建议 |
| `virtual` | ✅ 逻辑飞（画面不动） | **最好** | 演示侦查→打击全链路 |

## 二十、自研"动力学"：关重力、保留物理（`set_enable_gravity`）

### 为什么不是写一个真的动力学引擎

我们本来就有一套自己的运动学引擎（圆弧过渡 + 等距重采样 + 偏航限速 + 爬升 + 限速位移）。
失败的从来不是"算法"，而是**我们算好的位姿会被物理引擎的重力拖走**：

```
ALT DRIFT UAV1: 设定 19.5 m，实测 10.6 m（差 -9.0 m）
速度：0 → 37.6 → 164 → 220 → 366 m/s     （9.8 m/s² 自由落体累积）
```

所以真正要解决的是"重力"，不是"写动力学"。

### 三条已被排除的路

| 做法 | 结果 |
|---|---|
| 每帧 `set_transform` | 位置能写，速度照样累积 |
| `set_target_velocity(0,0,0)` | **空转**：不报错、也不生效（日志确认无异常） |
| `set_simulate_physics(False)` | **UE4 崩溃**（`VehicleAnim != nullptr`） |

### 找到的第四条路：`set_enable_gravity(False)`

扫 `swarmae_lib/libcarla.cp36-win_amd64.pyd` 的符号表，确认存在：

```
set_enable_gravity      ✓
enable_gravity          ✓
drag_coefficient        ✓（备选）
VehiclePhysicsControl   ✓（备选）
attach_to / add_impulse ✓（备选）
```

`set_enable_gravity(False)` **只关重力、保留物理**，所以不会触发
`set_simulate_physics` 那条会崩的代码路径。

实现：每架机在复位时先关重力，再摆位置；并且每帧仍然 `set_target_velocity(0,0,0)` 兜底。

```python
self._disable_gravity(actor, name)      # 先关重力
actor.set_transform(...)                # 再摆位姿
actor.set_target_velocity(0, 0, 0)      # 兜底清速度
```

### 怎么验证成功

日志里会出现：

```
GRAVITY OFF UAV1
GRAVITY OFF UAV2
GRAVITY OFF UAV3
```

心跳里速度应恒为 `[0.0, 0.0, 0.0]`，机高平滑爬到 250 并稳住。

如果出现：

```
GRAVITY: UAV1 没有 set_enable_gravity，无法关重力（会持续下坠）
```

说明这个 actor 不暴露该接口，那就退回 `--uav-mode virtual`（逻辑飞行，画面不动）。

### 两种模式的分工

| 模式 | 3D 画面能看到飞机飞吗 | 稳定性 | 建议 |
|---|---|---|---|
| `kinematic` + 关重力 | **能**（如果 `set_enable_gravity` 生效） | 取决于验证结果 | 先试 |
| `virtual` | 不能 | 100% 稳定 | 保底方案 |
