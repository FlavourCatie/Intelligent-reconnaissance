> 面向对象：本组 3 名技术同学 + 需求经理
> 目的：说清楚"现在有什么、哪些能用、缺什么、在哪里改"
> 所有结论都在本机核对过（含实测坐标、实测依赖、实测文件大小），标注「实测」的地方可以直接引用来对齐需求。

## 0. 一句话结论

现有代码给的是**零件**，不是**剧情**。

```
A*（有）  Stanley/PID（有）  队形点计算（有，但没接线）
探测 detect（有）  开火 set_weapon（有）  坐标转换（有，但数值写死）
──────────────────────────────────────────────────────────────
把上面这些串成「无人机发现 → 传信息 → 无人车打击」的时序流程  ← 没有
```

所以 3 人的工作量里，**大约 20% 是改算法，80% 是写"流程层"**：状态机、任务分配、通信建模、时序编排、可视化。
不要想着重写 A* 或 Stanley——那两份代码已经能跑，性价比极低。

## 1. 先把运行链路搞清楚（这是所有问题的前提）

`Materials/readme.txt` 写了顺序，但没写为什么。补全如下：

| 步 | 操作 | 作用 | 产物 / 端口 |
|---|---|---|---|
| 1 | `CarlaUE4 - 快捷方式` | 启动 UE4 城市地图 | 3D 场景，监听 2000 |
| 2 | `Materials/simu_driver_windows/start.bat` | 启动飞控/通信驱动 | 会问你 `1. 固定翼 / 2. 旋翼` |
| 3 | `Materials/practice/practice1_Scene/subject4.exe` | **按 json 生成 3 车 3 机 + 敌人** | 读取同目录 `vehicles.json` `targets.json` `game.json` `elements.json` `rands.json` |
| 4 | `python 你的算法.py` | `SwarmAEClient(ue_ip="127.0.0.1", ue_port=2000)` | 注册节点 → 控制 → 探测 |

### ⚠️ 第 2 步的选择会改变无人机怎么飞

`start.bat` 里用的是 `sed.exe` 直接改 `bin/driver/config.yaml` 的 `Type:` 字段：

* `1` → `fixed_wing`：**固定翼，不能悬停**。`uav_control.py` 里那种「飞到 z=15 停住等」的写法在物理上不成立。
* `2` → `quadrotor`：四旋翼，可以悬停。

**这是第一个必须和需求经理确认的事**：演示里无人机是"盘旋待命"还是"悬停待命"，直接决定中继和侦察的实现难度。建议用 `2`（旋翼），与课程任务说明里的"无人机组成通信网"最匹配。

## 3. 三个入口脚本，逐段讲

### 3.1 `plan.py` —— "算一次路径 + 打一轮炮"的演示

| 行 | 内容 | 说明 |
|---|---|---|
| 77-82 | 建连接，连调 4 次 `stage_start/stage_complete` | 只是为了满足接口，**不是真的分阶段**。演示时要改成真时序 |
| 85 | `get_road_network()` 拿 `img/scale/world_offset` | 拿到 4794×4794 路网图，`scale=1` |
| 89 | `skeleton_refinement(img)` | 骨架细化，**会在当前目录写 68MB 的 tga**（见 §9） |
| 95-111 | 注册 3 车（no 1-3）+ 3 机（no 4-6） | `no` 必须和 `vehicles.json` 里的顺序一致 |
| 115-124 | 起点取 UGV1 位置；**终点写死 (-1500, -217)** | 终点离起点只有 ~295 m，是教程玩的玩具终点，**必须改成敌方目标区** |
| 127 | `skeleton_point()` 把起终点吸附到最近白点 | 因为 A* 要求起点必须在路上 |
| 134-135 | A* 规划 | 见 §4.2 |
| 143-151 | 像素 → 世界 → B 样条加密 | `ReferencePath(..., resolution=2)` |
| 153-158 | `detect_fun()` 探测 → `set_weapon(ob, 0..4)` 连打 5 个目标 | ⚠️ **探测不足 5 个目标时必然 IndexError** |

**这个文件里能直接复用的**：坐标转换、骨架吸附、A*、样条加密、探测+开火调用姿势。
**必须重写的**：终点、分期、循环、目标选择逻辑。

### 3.2 `plan_control.py` —— 唯一有完整闭环的文件（改造主战场）

核心循环（182-298 行）每一步在干什么：

```
 ┌─ 读 3 台车的位姿 + IMU        (185-195)
 ├─ 判断 1 号车到终点？→ 刹车 10s → 拉手刹 → break   (198-211)
 ├─ 记录轨迹 history              (214-221)
 ├─ matplotlib 实时画            (224-226)
 ├─ 每车沿"前视点"找参考路径最近点 (230-232)
 ├─ 算目标速度                   (234-252)
 │    v2 = v1 + 0.1*(dist(v1,v2) - s0)     ← 跟驰（车距保持）
 │    v3 = v2 + 0.1*(dist(v2,v3) - s0)
 ├─ Stanley 算转向 / PID 算加速度 (255-262)
 ├─ 映射成 steer / throttle / brake  (265-294)
 └─ apply_control 下发            (292-294)
```

**这个文件里的 5 个已知问题（改动前务必知道）：**

| # | 位置 | 问题 | 后果 |
|---|---|---|---|
| 1 | 270-275 | `else` 分支把 `throttle_1/brake_1` 写成了 `throttle/brake` | 只要某刻 `accel_1 <= 0` 且是第一次进这个分支 → **NameError** 崩掉 |
| 2 | 224-225 | `ref_path_2 = ref_path_1`，三车**完全同一条参考线** | 三车会叠在一条线上，**"列队"根本没有实现**。`formation_calculate.offset_path()` 就是干这个的，但没调用 |
| 3 | 238-252 | `time<4` 和 `time>=4` 两个分支代码**完全相同** | 死代码，删掉即可 |
| 4 | 198 | 只有 1 号车判断到点，且用的是"路径最后一点" | 2、3 号车可能还没到就 `break` 了；演示时会被看出"车没停好" |
| 5 | 179 | `dt = 0.01` 是写死的初值，之后用实测 `dt` | 第一帧 PID 微分项会爆炸，建议 `dt` 初值给 0.1 |

另外 `lib/swarm_api.py:78` 的 `struct.State(pose, imu.v, imu.a, imu.rate_yaw)` —— 第 4 个位置参数在 `State.__init__` 里是 **`kappa`（曲率）**，这里塞了偏航角速度。目前没人用 `kappa` 所以没爆，但别在局部规划里信这个值。

### 3.3 `uav_control.py` —— 只有 26 行是真正有用的

* **1-112 行**：和 `plan.py` 逐字相同（复制粘贴留下的）。真正用到时第一件事就是把这 112 行删掉，改成 `from lib import ...`。
* **113-130 行**：等三机升到 `z=15` 才继续 —— 但是 `subject4.exe` 里无人机初始 `z=10`，所以要靠同一个循环里的 `target_point_control(..., z=15)` 把它顶上去。**`15` 是写死的悬停高度**，和侦察/中继高度需求耦合，必须参数化。
* **132-139 行**：三种"相对位移"（+25 m 横移 / +25 m 升高 / -25 m 横移）。这就是原始的"队形"，但三机之间没有共享参考路径，飞完就散了。

> 结论：`uav_control.py` **不具备航线规划能力**，只演示了"给目标点 + 给地速"的简化飞控。

## 4. 必须重点关注的 6 个模块（按投入产出排序）

### 4.1 ⭐⭐⭐ `lib/swarm_api.py` —— 所有交互的唯一出口

`Vehicle` 类把「无人机」和「无人车」统一了，`_check_type()` 防止你调错接口。

| 方法 | 行 | 干什么 | 备注 |
|---|---|---|---|
| `get_transform()` | 68 | 位置 + 航向（**yaw 已转弧度**） | 最常用 |
| `get_state()` | 75 | `pose + v + a + rate_yaw` | 给控制器吃 |
| `apply_control()` | 81 | 车的油门/转向/刹车/手刹 | 参数会被 clip |
| `target_point_control()` | 204 | **机的"给目标点+地速"飞控** | `control_kinetic_simply_global` |
| `detect_fun()` | 101 | 解析 `detect_situation()` 的 JSON | ⚠️ 见下 |
| `set_weapon()` | 159 | 按目标类型选弹种并开火 | ⚠️ 见下 |

**`detect_fun()` 的 3 个坑：**

1. **`global res`**（107 行）—— 用了全局变量，多线程/多车会互相踩。
2. **坐标写死**（141-142 行）：`x1 = int(x1 + 2095)`、`y1 = int(y1 + 2637)`。实测这两个值 = `-world_offset`，是对的，但一旦换地图就全错。→ 应统一走 `WorkPlace/tools/coord.py`。
3. **单位可疑**（137 行）：`x1 = i['Position']['X'] / 100`。但 `get_location()` 的返回值被 `plan.py` 直接当**米**用（没除 100）。两者必有一个错。→ **先跑 `tools/unit_check.py` 定案**。

**`set_weapon()` 的 2 个坑：**

1. 类型名是三套写法混用：这里比 `'Barricade_BP' / 'Stryker' / 'Building' / 'Soldier'`，`data_struct.calculate_collision_radius()` 比 `'BP_BarricadeHard' / 'Barricade_BP' / 'Stryker'`，官方文档写的是 `Barricade / Stryker / Pillbox / Building / Soldier`。→ **必须实测拿到真实 `Type_Name`，做一张映射表**。
2. 参数顺序和文档不一致：文档表格列的是 `(x, y, z, ammo_type, ammo_number)`，这里实际调用是 `(3, 1, x_ue, y_ue, 1.5)` —— 即 `(弹种/武器号, 数量, x, y, z)`。**以现在能跑的写法为准**，但要在首帧打出来验证。

### 4.2 ⭐⭐ `lib/global_planner.py` —— A*

* 8 邻域栅格 A*，**白点可走（`map_image[y][x] != 0`），黑点不可走**。
* 设计意图：预留了"远处大步走、`h_cost < search_range(40)` 时把 `step_size` 缩到 1"的**靠近终点精细化**机制（83-96 行）。但注意 `step_size` 默认就是 `1`，所以**不显式传更大的 `step_size` 时这段逻辑是空转**——想提速得自己传，例如 `AStar(..., step_size=4)` 再靠这段收尾。
* **性能是真问题**：`open_list` 是 list，每轮线性找最小 `f`，路径几千步 → O(n²)。在 4794×4794 全图上跑，`scale=1` 时会明显卡顿。
  → **建议**：① 用 `AStar(..., scale=4)` 把图降到 1200×1200 先快速出粗路，再局部细化；② 或把 `open_list` 换成 `heapq`。这一步能把规划从"分钟级"压到"秒级"，演示时不容易翻车。

### 4.3 ⭐⭐ `lib/image_process.py` —— 骨架 + 吸附

* `skeleton_refinement(img)`：RGB → 灰度 → 二值(>0.5) → `skimage.skeletonize` → 存盘。
* `skeleton_point(...)`：把任意坐标吸附到最近的白点（路网骨架），**这是把"目标点/合围点"落到可行驶道路上的关键工具**，合围选点、中继悬停点都要用它。
* ⚠️ **副作用**：每次调用都往**当前工作目录**写 `skeletonized_image.tga` + `.png`。实测那个 tga 是 **68,947,352 字节（约 68 MB）**，因为 4794×4794×3 未压缩。一天跑几十次就是 GB 级垃圾。→ 改成返回数组、或写到 `temp/` 并加开关。

### 4.4 ⭐⭐ `lib/controller.py` —— PID + Stanley

* `PID`：标准位置式 PID，`Kp/Ki/Kd` 可调。`plan_control.py` 用的是 `Kp=0.1, Ki=0, Kd=0`。
* **`Stanley` 有两套实现，不要混用**：
  * `update_control(P1, ego)` —— 吃 `Transform`，返回 `delta`，内部有 3 个魔数（`0.2/0.3/0.45`）。`plan_control.py` 用的是这个。
  * `StanleyControl(x, y, yaw, ...)` —— 吃裸坐标，返回 `(steer, lat_err)`，含速度自适应增益 `k_y = min(0.091, 1.215/v)`。`formation_calculate.control_step()` 用的是这个。
* `plan_control.py:265` 把 `delta / (pi/6)` 映射成 `[-1,1]` 的 steer，`formation_calculate.py:309` 用 `delta / 1.8` —— **两处标定不一致**，换控制器时要重新整定。

### 4.5 ⭐⭐⭐ `lib/formation_calculate.py` —— 最值钱、最可惜

**这是一个已经写好的编队库，但全项目没有任何地方 `FormationToolkit()` 实例化过（实测 grep：0 处调用）。**

| 方法 | 行 | 能力 | 对应课程要求 |
|---|---|---|---|
| `calculate_formation_position(n, r, type)` | 33 | 4 种队形：①纵向一字 ②横向一字 ③正多边形顶点朝纵 ④正多边形顶点朝横 | **一字 / V 字 / 倒 V** 都能用 ③④ 加旋转得到 |
| `formation_offsets_from_positions(positions)` | 83 | `(x,y) → (lateral, longitudinal)`，即把队形点变成"沿路径的左右/前后偏移" | 把队形贴到任意弯曲路径上 |
| `offset_path(ref, lat, lon)` | 153 | 沿法线平移 + 沿弧长前后平移，返回新的 `ReferencePath` | **给每台车生成各自的参考线**（正是 `plan_control.py` 缺的） |
| `update_formation(task_msg, ...)` | 246 | 从消息里读 `formation_type/formation_radius`，输出 N 条偏移路径 + 期望车间距 | 队形切换 |
| `control_step(...)` | 265 | **完整的编队控制**：前视点 → Stanley → 车间距误差 → 速度指令 → 油门刹车 | 可以直接替换 `plan_control.py` 的循环体 |

**唯一障碍**：`update_formation` 依赖 `task_msg`（protobuf 消息，来自 `lib/udp.py` 的 5003 端口）。而 `proto/` 包**不存在**，Windows 下这条路走不通。
→ **改法**：写一个 3 行的 `FormationCmd` 数据类（`formation_type: int`、`formation_radius: float`），或者直接从命令行/配置文件读，把 `update_formation` 的签名从 `task_msg` 换成 `FormationCmd` 即可。

### 4.6 `lib/frenet_optimal_planner.py` —— 只用两个类

* **在用**：`ReferencePath`（三次 B 样条 + 等弧长重采样 + 航向 + 曲率）、`VehicleGeometry`（画车/做碰撞）。
* **没在用**：`FrenetOptimalPlanner`（27KB 的完整 Frenet 规划器）、`check_collision_free`。
* 教程 readme 原话："局部规划（很难。不讲）"。**建议不碰**——除非需求经理明确要求"避障演示"。

## 5. 缺口清单：需求 vs 现有能力（这张表决定你们要写什么）

| 任务 | 课程要求（PPT 原话） | 现有零件 | **缺什么（要新写）** |
|---|---|---|---|
| **机动/编队** | "从起点行驶到终点，途中按需求变换队形，包括 V 字、一字、倒 V" | `formation_calculate` 全套（未接线）；`plan_control` 跟驰 | ① 队形调度（何时切、切什么）② 三车**各自**参考线 ③ 切换时的连续性（不能跳变） |
| **侦察** | "规划无人机最短侦察路径，获取敌方目标；再据此规划三车路径遍历打击" | `uav_control` 逐点飞；`detect_fun` 能探测 | ① 区域覆盖规划（牛耕/骨架 TSP）② 禁飞区约束 ③ 3 机分区 ④ **`submit_plane_route` / `get_key_points` 完全没用上** |
| **打击** | "三车从不同位置包围目标，**目标需落在三车形成的三角形内**" | `set_weapon` 能开火；A* 能到点 | ① 合围选点 ② 三角形内点判定 ③ 目标-车分配 ④ 打击时序（谁先打、打几发） |

## 6. 修改点地图：改哪个文件、哪个函数、怎么改

### 6.1 通信遮挡 + 中继（完全新写，优先级最高）

这是需求经理最看重、同时也是现有代码**零基础**的一块。

#### ① 遮挡怎么建模

SDK 的 `detect_situation()` 文档只写"探测半径内的 Actor"，**没有任何视线/遮挡参数**。所以"被建筑遮挡"必须自己算。

最省事且可信的做法：**直接用路网图当建筑掩膜**。

```python
# WorkPlace/core/comm.py 思路
mask = np.array(Image.open("roadnet.png").convert("L")) > 0   # 白=路，黑=建筑/空地

def los_blocked(p1, p2, step=2.0):
    """p1,p2 为世界坐标(米)。沿连线每 step 米采样，落在黑区即判定遮挡。"""
    d = math.dist(p1, p2)
    for k in range(1, int(d / step)):
        t = k * step / d
        x = p1[0] + t * (p2[0] - p1[0])
        y = p1[1] + t * (p2[1] - p1[1])
        px, py = coord.world_to_pixel(x, y)
        if not mask[py, px]:
            return True
    return False
```

**必须在报告里写清假设**：路网图的黑色既包含建筑也包含不可行驶空地，所以这是**保守近似**（会高估遮挡）。这比假装没遮挡强得多，也是答辩时能加分的点。

#### ② 一个必须知道的物理事实（能救你们）

无人机在 **z=15~100 m** 高度、半径 300 m 内，**几乎不会**被 30~60 m 高的楼遮挡。真正会被遮挡的是：

* **车 ↔ 车**（都在地面，隔着街区）
* **低空机 ↔ 车**

所以中继任务的正确卖点是：**"两车被街区挡住 → 无人机升空搭桥"**，这和课程 PPT 第 8 页「无人车之间距离较远，无法直接通信，无人机组成通信网」**完全对得上**。不要写成"无人机之间被遮挡"，那样既不真实也不好演示。

#### ③ 半径 R 的矛盾（**必须先和需求经理确认**）

| 来源 | 数值 | 换算 |
|---|---|---|
| `vehicles.json`（实测） | UAV `detectRadius = 30000`，UGV `= 10000` | 若单位是**厘米** → **300 m / 100 m** |
| 路网图（实测） | 4794×4794 px，`scale=1` | 图幅 **4.8 km × 4.8 km** |
| `game.json` 的 arena（实测） | x∈[-1900.3, 2277.4] | 宽 **4177.7 m**（按米理解才填满图幅，按厘米只有 41 m，荒谬） |
| 目标距起点（实测） | 最近 17 m，**最远 4041 m** | — |
| 需求经理口述 | "20 km 信息传递半径" | 覆盖全图还有余 |

**结论**：如果 R 真是 20 km，那么**一架无人机就能覆盖整个战场，中继任务在数学上退化成 1**，没有演示价值。
两种可能：① R 应该是 300 m（配置文件里的值）；② "20 km" 是真实装备指标，但仿真里要按"有效通信距离"打折。
→ **演示策略：把 R 做成可调参数（默认 300 m），现场画通信圆，讲"R 从 300 m 放大到 20 km 时，最少中继机从 3 架降到 1 架"**。这样无论需求经理怎么理解，你们都有话说。

#### ④ 最少中继点算法（链式覆盖）

```
两车 A、B 距离 d（用路网 A* 距离而不是直线距离更好讲）
有效半径 R_eff = R * 0.8                     # 留 20% 裕度
最少机数 n = ceil(d / (2 * R_eff))            # 每架覆盖 2 段，搭桥
若 n > 3：说明该任务用 3 机不够，向需求经理报告（这本身就是一个好结论）
候选点：把 AB 连线按 n+1 等分得到理想点
       → 用 skeleton_point() 吸附到最近路口
       → 用 los_blocked() 校验 A-中继、中继-B、中继-中继 三段可见
       → 不可见则该点沿法线左右各移 20/40/60 m 重试
高度：取 z = max(楼高) + 20，或直接用 60~80 m
```

**验收标准（可以写进 PPT）**：屏幕上画出 3 个通信圆 + 2 条车-车链路，链路在无人机就位前是红色（断），就位后变绿（通），并显示"使用 2 架中继机（方案最少）"。

### 6.2 合围打击

**几何部分很干净**，直接在 `WorkPlace/core/encircle.py` 写：

```python
def encircle_points(target, r=120.0, phase=0.0):
    """以 target 为圆心、r 为半径，按 120° 取 3 点（理想圆上）"""
    return [(target[0] + r * math.cos(phase + k * 2*math.pi/3),
             target[1] + r * math.sin(phase + k * 2*math.pi/3)) for k in range(3)]

def inside_triangle(p, a, b, c):
    """叉积同号法：三点在同侧则 P 在三角形内"""
    def cross(o, u, v):
        return (u[0]-o[0])*(v[1]-o[1]) - (u[1]-o[1])*(v[0]-o[0])
    d1, d2, d3 = cross(a,b,p), cross(b,c,p), cross(c,a,p)
    has_neg = (d1 < 0) or (d2 < 0) or (d3 < 0)
    has_pos = (d1 > 0) or (d2 > 0) or (d3 > 0)
    return not (has_neg and has_pos)
```

**但有个现实问题必须处理**：城市是**方格路网**，把理想圆上 3 点吸附到道路后，三点很容易**接近共线**（都在一条横街或竖街上）→ 三角形退化 → 目标跑到三角形外。

**处理办法（这是一个很好的"算法优化"讲点）**：

```
1. 候选角度集合：{0°,120°,240°} 起步，不行就遍历 phase ∈ [0°,360°) 每 15° 试一次
2. 每个候选点：
   ideal = 圆上点 → snap = skeleton_point(ideal)（吸到路上）
   记录 |snap - ideal|（吸附误差）
3. 筛选条件（三条全满足）：
   a) inside_triangle(target, snap0, snap1, snap2)
   b) 三车 A* 都能到达（不可达则该候选丢弃）
   c) 三个 snap 两两间距 > 2*车长（否则车会挤在一起）
4. 在满足条件的候选里，取"三车 A* 总路程最短"的一组
```

**分配**：3 个目标点 → 3 台车，用最小总路程的**全排列**（3! = 6 种，直接暴力枚举即可，不用匈牙利算法）。这是最省事且结果最优的做法，答辩时也好解释。

### 6.3 编队（机动任务）

**改哪里**：`plan_control.py` 的 224-225 行。

```python
# 现在（错）：三车同线
ref_path_2 = ref_path_1

# 改成：用 FormationToolkit 生成 3 条偏移线
kit = FormationToolkit()
```

### 6.4 侦察（无人机）

现有 `uav_control.py` 只有"给点飞"，**没有覆盖规划**。两条路：

**路线 A（推荐，能拿分）：用官方航线接口**
`SwarmAEGame` 有 `submit_plane_route(routes)`（阶段 1 一次性提交所有飞机航线，格式 `[{"node_id":"1","route":[{"x":..,"y":..,"z":..}]}]`）和 `get_key_points()`（官方巡逻关键点）。**这两个接口现在一行都没用过**，而它们正是为"侦察阶段"设计的。用它 = 顺应评测逻辑。

**路线 B（保底）：继续用 `target_point_control` 逐点飞**
简单、可控，但航线要自己算。

**覆盖规划做法（两条路都要先算航线）**：
1. 把 `arena` 按 **2R×2R** 切成网格（R=探测半径，300 m → 600 m 格）；
2. 用**牛耕法（boustrophedon）**串成往返折线；
3. 扣掉 `no_fly_arena` 的 3 个多边形（点在多边形内判定）；
4. 沿折线每 50~100 m 取一个航点，`z` 设 60~100 m；
5. **3 机分区**：arena 沿 x 三等分，每机一块，飞完汇总。

**去重**：3 架机都会重复探测同一目标。用 `(round(x/10), round(y/10))` 栅格化去重，再和"上一帧已知目标"做增量对比，就能在界面上打"新发现！"的标注——**这是"无人机发现 → 传递信息"里最出效果的一秒**。
