# 这个项目是怎么一步步跑起来的

> 开发历程、踩坑记录和一些课程建议
> 不是正式技术报告，更多是回头看整个项目时的一些真实想法。

---

## 先说说最后做成了什么样

最后做出来的东西，简单说就是：

三架无人机先去半张地图上扫，敌人位置事先不知道；扫到目标以后，不是“看到谁就让最近的车冲过去”，而是先判断这个敌人是在普通路段，还是在丁字路口/十字路口。路段敌人可以单车处理，路口敌人尽量从两个不同方向合围。三台无人车在路网上开，平时编队走，接敌后分开，打完再释放，继续接无人机后面发现的目标。

这套东西听起来不复杂，但中间真的踩了很多坑。下面按开发过程慢慢讲。

---

## 一、开发历程：四个阶段

### 阶段一：飞控没调通，先把“流程”跑起来

最早的时候，无人机飞得很抽，起飞和悬停都不稳，根本没法拿真实飞行去做任务。那时候如果一直卡在飞控上，后面的侦察、派车、打击都没法推进。

所以我们先做了一个“退一步”的选择：无人机的飞行先按航线模拟走，位置用数学方式推进，探测也先用数学半径算。这样虽然画面里的飞机不是真实飞控在飞，但至少能把“发现目标 → 派车 → 到达 → 打击 → 结束”这条链路先跑通。

后来飞控调通了，无人机才真正加入任务流程。现在代码里还保留着三种模式：真实飞控、运动学播放、纯虚拟。它们不是为了炫技，而是因为早期确实需要一条“没有飞控也能调算法”的路。

也是在这个阶段，我们后来加了一个很关键的门限：**无人机没有完全升空、没有进入巡航之前，无人车不许动。**
以前出现过飞机还在爬升，车已经跑出去的情况，看起来就是“无侦测、无目标，车先动了”，很怪。现在这个门限把时序固定住了。

### 阶段二：小地图从“全城看个寂寞”改成“半图看清楚”

早期小地图显示的是整张 4.8 km 的全城图。道路、敌人、轨迹、禁飞区、雷区、电磁区全堆在一起，现场根本看不清，更别说判断车在干什么。

后来我们做了几件事：

- 不显示全城了，只显示当前任务区；
- 半图演示固定显示 `±1010 m`，道路和边界清楚很多；
- 背景压暗、半透明，只留下必要图层；
- 敌人只保留三种状态：空心圈是没发现，红色实心是已发现，黄色 X 是已消灭；
- 覆盖范围按 200 m 的格子记账，不会同一块地方反复叠色；
- 刷新从“每帧重画”改成 1.2 s 一次。

小地图这东西，看起来是显示问题，实际上很影响调试。地图看不清，后面所有问题都很难定位。

### 阶段三：多车一上来，追尾、让行、绕行全来了

单车跑通以后，三台车一起上，问题立刻变多：

- 后车跟太近，容易追尾；
- 前车一停，后车不知道该等还是该超；
- 绕行判定太严，车为了“安全”绕一大圈，最后卡在路口；
- 窄路和宽路用同一套超车逻辑，宽路能过、窄路卡死。

后来我们把这些拆开处理：

- 编队僚车用更紧的跟车距离，避免脱队；打击车反而留更大的安全距离，避免一头扎进交火区；
- 超车不再“固定往旁边偏 5 m”，而是先量挡路车两侧的真实路面宽度，哪边宽往哪边走；
- 让行分成普通让行和正面相遇：普通让 8 s，正面相遇让 12 s，让对方有时间完成借道；
- 绕行判定不再只看“离障碍物多远”，而是把路径长度、是否穿敌、接近方向、局部路宽一起看。

这一段最大的体会是：**多车问题不能靠一个“安全距离”参数解决，必须把跟车、让行、超车、绕行分开建模。**

### 阶段四：动态改派、合围、收尾

再往后就是动态改派和合围。

最早每次敌人被消灭，我们的做法是把那台车的 agent 删掉，再重新生成一个去接新目标。逻辑上没问题，但实际画面会卡一下，车辆姿态也会跳，甚至出现物理异常。后来改成不删车，只改目标：保留同一个车辆对象和同一个 agent，从当前位姿重新规划。画面就顺了。

合围是最后一个大头。最早的问题是：两辆车从同一条路来，一辆停下，另一辆直接穿过敌人绕到对面，看起来“合围条件满足了”，但过程完全不对。后来我们才明白，**不是“到两个不同阵位”就叫合围，车必须真的从不同道路绕过去。**

为此加了路线校验、绕行重算、阵位距离、最多两面等限制。到最后，半图里的第一个路口能做到一辆从 W 侧、一辆从 S 侧绕行过来，打完以后释放，再去下一个目标。

## 二、十二个坑，以及当时是怎么想的

### 坑 1：飞控不稳，只能先模拟飞行

一开始无人机飞得抖，真实飞行根本没法作为任务的一部分。我们当时也纠结过：是继续死磕飞控，还是先把任务逻辑跑起来？

最后选的是后者：先把航线、探测、任务流程用模拟方式跑通，等飞控稳定了再切回真实飞行。

这个决定现在看是对的。否则整个项目会一直卡在“飞机为什么抖”上，后面的多车协同根本没机会做。

后来飞控调通，无人机正式加入任务流程，模拟模式也没有删，留作调试和对比用。

### 坑 2：小地图太大、太乱，什么都看不清

这个问题前面说过，本质是“信息密度”问题。

一开始想着“全局地图信息全”，结果全城图在屏幕上只有一小块，敌人和车都挤在一起。后来改成局部地图，只显示任务区，反而更清楚。

我们还踩过一个误区：以为是画得不够多，其实是画得太多。把不重要的标注去掉、背景压暗以后，重点自然就出来了。

### 坑 3：无人车追尾，绕行又太容易卡住

这个问题其实是两个极端：

- 跟得太紧，追尾；
- 绕得太保守，卡死。

一开始想用一个“安全距离”同时解决，后来发现不行。跟车是跟车，绕行是绕行，超车是超车，得分开。

最后的处理是：

- 编队跟车更严格，僚车保持更紧的间距，避免掉队；
- 打击车保留更大的前车距离，避免冲进交火区；
- 超车先量路宽，窄路不硬超；
- 让行分普通和正面相遇，给彼此留时间；
- 绕行判定放松一点，但用路径长度和局部路宽兜底。

### 坑 4：动态改派时删车、重建车，视角卡顿

这个问题很典型：逻辑上“删掉旧任务、生成新任务”很自然，但放到仿真里，删车/重建会带来姿态跳变和物理异常。

后来改成“车还是那台车，只换目标”。编队里的车要分裂成打击车，也只是换角色，不重新生成。

这个改动看起来小，但对画面稳定性的提升非常明显。

### 坑 5：全区域测试太慢，于是用了传送

这个问题很现实：每次测试都从场地西侧开到任务区，光路上就要很久，调试效率很低。

所以测试阶段用了传送/开局展开，把车直接放到测试区域附近。这样一天能多跑很多轮。

但我们也清楚，传送只是测试手段，不是最终流程。最后半图演示专门做了“无传送”模式，从原始出生点出发，验证真实情况。

### 坑 6：传送把车传进建筑里

传送用多了，又出了新问题：落点没吸附到道路，车直接出现在建筑边上，甚至撞进去。

后来的处理很朴素：所有落点先吸附到最近的道路，开局展开点只从“任务区内、离边界够远、在最大连通路网上、路宽够”的骨架点里选。场景里的原始出生点也重新放回道路。

所以后来即使不传送，车也能从左侧边界沿着路进入任务区。

### 坑 7：任务没全局完成就卡死，原因是目标数量没统一

有一段时间，敌人明明打光了，任务却不结束；有时候又提前结束，看起来像“卡死”。

查下来不是状态机本身的问题，而是“场景里到底有多少敌人”和“运行中认为有多少敌人”不是同一个数。`targets.json` 里是一份，运行态里又是一份，两边对不上。

后来统一成：启动时从 `targets.json` 统计总目标数，击杀点单独记录，完成条件要求“击杀数达到总数，且已发现目标都有对应击杀点”。

这件事的教训是：**任务完成判定一定要有唯一的真值来源，不能这里数一个、那里数一个。**

### 坑 8：随机撒敌人，撒到出生点、路口中心

随机撒点一开始很“随机”，但随机不等于合理：

- 敌人可能出现在出生点旁边，开局就被压；
- 敌人卡在十字路口正中间，无人车转弯判定直接乱掉；
- 路口敌人和路段敌人混在一起，派车策略也不对。

后来撒点工具加了约束：只落在任务区路网、离出生点远一点、离路口中心远一点、避开禁飞区。路口敌人单独指定，不和普通敌人混在一起。

另外还加了无人车自己的补盲：无人机没看到的目标，车辆近距离看到以后也会并入任务池，不会“看不见就不管”。

### 坑 9：按“最近原则”只派一辆车，完全没有配合

最早是“发现一个敌人，派最近的一辆车”。目标少的时候，经常只有一辆车出动，另外两辆在原地看戏。

后来引入编队：目标少的时候，三辆车先靠拢，按纵队/楔形一起走；接敌以后再分开，该打的打，该跟的跟。这样不会三辆车各跑各的，也不会浪费单独跑路的时间。

编队不是为了好看，是为了让“目标少”的时候也有协同，接敌时还能化整为散。

### 坑 10：小地图黄圈不稳定，其实不是显示问题

有一阵子一直以为是小地图画黄圈的逻辑有问题：圈的位置跳、数量不对。

后来查下来，显示层只是“背锅”。真正的问题是：这个路口敌人和原来的寻路/分配逻辑冲突，车辆到底能不能从那个方向来、能不能到阵位，状态一直在变，黄圈自然也跟着变。

所以后来不是改画图，而是改战术层：路口目标单独登记、单独校验路线、单独维护合围状态。显示层只负责显示“确实有效的合围目标”。

这件事对我影响挺大：**看到显示异常，先别急着改 UI，先看它背后的状态对不对。**

### 坑 11：合围时全从同一侧来，甚至直接压过敌人

这是合围里最核心的问题。

一开始我们只看“两辆车有没有到两个不同阵位”，结果出现：

- 两辆车从同一条路来；
- 一辆停下，另一辆直接穿过敌人，绕到对面；
- 看起来满足“两个方向”，但过程完全不是包抄。

后来才想明白：**阵位在两边，不代表车是从两边来的。**

于是加了路线校验：

- 路径不能穿过敌人；
- 路径不能贴着其他还没处理的敌人走；
- 绕行不能太离谱；
- 最后一段的接近方向必须和“从该分支外侧过来”一致；
- 实在直连会穿敌，就把敌人挖掉，重新算一条绕行路。

同时把阵位距离拉开，不再贴着敌人停，避免“压过去”。合围最多做两面，因为第三面经常要绕一两公里，等太久。

半图里能看到 W 侧和 S 侧两辆车真的从不同道路过来，这个效果是一点点调出来的。

### 坑 12：三车全程一字型，没有队首队尾变化，也没有化整为散

这个问题其实是“协同”和“分散”的平衡。

有一段时间，三辆车为了保持队形，全程一字型，谁也不敢分开；接敌时也没有明显的“化整为散”，看起来就是三辆车排队走。

后来我们的思路是：平时编队，接敌分裂。目标少时保持队形一起走，发现目标后，该分裂的 split 成打击车，该跟的继续跟，打完再重新组织。

这里要说明一下：你提到的“任务栈”，思路是对的，但我后来翻代码发现，**当前代码里并没有一个叫 `TaskStack` 的类**。真正落地的是：

- 任务池：维护当前有哪些目标；
- 优先级：按最晚到达时间、阵位覆盖、等待时间做分配；
- 状态机：合围、待机、跟随、分裂、冷却；
- 角色切换：领航、僚车、打击车。

它起到了“任务栈”的效果，但不是标准数据结构意义上的栈。这个区别我后来也吃了亏：如果汇报时直接说“任务栈”，别人一翻代码找不到对应类，会很尴尬。更准确的说法是“优先级任务池 + 状态机”。

## 三、这个项目我觉得比较值的地方

### 1. 敌人随机分布也能打

不是固定坐标、固定脚本，而是敌人位置由场景/撒点决定，程序不假设敌人在哪。无人机先扫，扫到谁再决定怎么打。

这个适应性是项目里最有价值的东西之一。换一张图、换一组敌人，框架还能用。

### 2. 侦察、打击、机动真的串起来了

不是三个模块各写各的：

- 侦察结果决定任务池；
- 任务池决定派车、编队、合围；
- 机动为打击服务；
- 打击结果又改变下一轮派车。

这三个环节是互相影响的，不是“先侦查完再打击”的流水线。

### 3. 分层比较清楚

传输/接口层、决策层、对象层、终端层，各自职责比较明确：

- 底层负责 SDK 调用、坐标、探测、控制；
- 战术层负责分类、阵位、分配、路线；
- 对象层负责单车/单机行为和编队状态；
- 终端层负责小地图、计划文件、日志。

层与层之间用 JSON 和函数接口隔开，出问题的时候能定位到某一层，不会一锅粥。

### 4. 调试过程本身也成了资产

这个项目很多进展不是“写出来的”，是“查出来的”：

- 视角卡顿 → 删车/重建；
- 黄圈乱跳 → 路线与目标状态；
- 全局完成卡死 → 目标数量不统一；
- 穿敌 → 只有 ETA、没有路径穿敌校验。

这些问题和对应的解决思路，比最后那段演示视频更能说明我们到底做了什么。

## 四、回头看，还有几个没完全解决的问题

有些问题不是没发现，是当前阶段没继续往下做：

1. **合围最多两面**
   第三面经常要绕很远，时间上不划算。现在是一个工程折中，不是所有路口都能三面。

2. **目标跟踪还不够正式**
   现在是聚类 + 固定代表点，没有多帧 ID、置信度、航迹管理。尸体/残影有时会影响击杀判定。

3. **传感器模型不严格**
   车辆探测有视场和遮挡，某些角度下 24 m 阵位可能看不到目标。现在用目标锁定、近距离刹停、击杀标记来兜底，但不是严格传感器仿真。

4. **A* 还是骨架 A***
   1 像素宽的路网，不是完整车辆运动学。窄路会车、死胡同、动态障碍，还是靠倒车/超车兜底。

5. **规模固定**
   三机三车，目标多了分配会截断；没有任务时间窗、弹药、风险这些约束。

6. **没有通信/弹道模型**
   跨进程用 JSON 文件，没有延迟/丢包；武器是离散事件，不含弹道和命中概率。

这些问题写出来不是为了否定项目，而是知道下一步该往哪走。

## 五、如果让我给课程提点建议

### 1. 别只给“侦察、机动、打击、中继”四个词

这四个词本身没错，但太抽象了。学生很容易变成“四个模块各做一点”，最后拼不到一起。

更好的方式是给一个核心场景，比如：

> 以侦察为核心：无人机先在未知区域发现目标，再根据目标位置/类型决定直接打击还是合围；机动服务于到达阵位和编队协同；打击服务于不同目标类型；中继作为可选的通信增强。

这样学生会自然地去想“侦察结果怎么影响打击”，而不是四个词各写各的。

### 2. 给一些能参考的案例

比如我们这个项目：

- 以侦察为核心，对地形、敌人分类，派发任务；
- 机动作为寻路和编队策略，提高打击效率，避免过度分散；
- 打击根据敌人位置决定单车还是合围；
- 从一个整体任务，慢慢加入模块，而不是一开始就堆四个子系统。

有案例，学生才知道“做到什么程度算串起来了”。

### 3. 分阶段验收，别只看最后视频

可以分成：

1. 固定坐标、固定场景：先验证单机/单车接口；
2. 随机敌人、未知位置：验证覆盖侦察和目标管理；
3. 编队/合围：验证多车协同和路线；
4. 异常情况：验证释放、重派、超时、失败。

每阶段给指标：完成时间、击杀数、碰撞/卡死次数、无效绕行距离、覆盖率。

### 4. 给接口和测试脚手架

课程可以提供：

- 场景/目标文件格式；
- 车辆/飞机接口的假 SDK；
- 小地图/日志的观测要求；
- 典型失败案例：追尾、穿敌、只派一辆车、全局完成判定错误。

这样学生能把精力放在算法和系统设计上，而不是反复猜接口。

### 5. 鼓励记录“负面结果”

这个项目很多进展来自“先复现 bug，再定位”。如果课程只要求交一个成功视频，学生会把失败过程都藏起来。

可以要求每组记录“失败现象—根因—修复—回归”，这比只看成功画面更能反映工程能力。

---

## 六、最后一点感受

这个项目最难的地方，不是某一个算法，而是“让很多看起来都对的小逻辑，在同一套系统里同时成立”。

飞控、地图、目标数量、车辆跟驰、绕行、合围、释放，每一个单独看都不复杂，但放在一起就会互相影响：

- 地图显示不对，可能是路线不对；
- 车辆卡住，可能是目标分配不对；
- 任务不结束，可能是目标数量不对；
- 合围看起来成功，可能是车从敌人身上压过去了。

所以后来我们养成了一个习惯：**先看状态，再看画面；先复现，再改代码；改完必须回归。**

这套习惯，可能比最后那段演示本身更有用。
